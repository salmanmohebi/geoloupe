# Contributing to GeoLoupe

Thank you for helping. This guide covers the development setup, the conventions, and how changes are
tested.

## Layout

```
src/geoloupe/           Python package
  config.py               YAML configuration (pydantic models)
  readers.py              open any format lazily with xarray
  grid.py, timeaxis.py    grids (dims, CRS, cell lookup) and time axes (calendars, matching)
  catalog.py              datasets → sources (resolution levels) → layers
  engine.py               the tile engine (level choice, budget, resampling, compositing)
  query.py                point values, time series, statistics, export
  points.py               point observations (stations) from Parquet/CSV/NetCDF
  vectors.py              vector overlays (GeoJSON, Shapefile, GeoPackage, GeoParquet, …)
  stac.py                 STAC searches and items → files of mosaic datasets
  gallery.yaml            the gallery of open public data (`geoloupe gallery`)
  overviews.py            overview pyramid builder
  formula.py, errors.py   error maps: formula language (same as frontend/src/lib/formula.ts) and
                          definitions (errors.json, shared with the web client; tests/formula_cases.json)
  errortiles.py           exact error tiles and statistics from native cells
  errorbuild.py           precomputed error maps (`geoloupe errors build`)
  colormaps.py/.json      lookup tables shared with the web client
  api/app.py              FastAPI routes
  server.py, cli.py       running it; command line
  demo.py                 synthetic demo data
  static/                 built web client (generated by `npm run build`; not edited by hand)
frontend/                 web client (TypeScript, React, MapLibre)
  src/lib/                pure logic: tiles, decoding, colormaps, Mercator math, URL state
  src/components/         UI components
  src/state/store.ts      application state (zustand)
  e2e/smoke.mjs           browser smoke test and screenshots (Playwright)
  e2e/gallery.mjs         browser test of the gallery: previews, every featured view, S3 browsing
  e2e/panes.mjs           browser test of the split panes (demo data)
  e2e/errors.mjs          browser test of the error panes (demo data)
  e2e/tour.mjs, readme-shots.mjs   the README animation and pictures (docs/images)
tests/                    Python tests (pytest)
examples/                 configurations and notebooks
docs/                     research, decisions, formats, configuration, benchmarks
```

## Setup

Python (≥ 3.11) with [uv](https://docs.astral.sh/uv/):

```bash
uv sync --all-extras          # creates .venv with all optional readers and dev tools
uv run pytest                 # ~115 tests, < 1 min
uv run ruff check src tests && uv run ruff format --check src tests && uv run mypy
```

Web client (Node ≥ 22):

```bash
cd frontend
npm ci
npm run dev                   # http://localhost:5173, proxies /api to http://127.0.0.1:8000
npm test && npm run lint && npm run typecheck
npm run build                 # writes ../src/geoloupe/static (commit it with client changes)
```

Run a server for the dev client: `uv run geoloupe demo-data demo && uv run geoloupe serve demo/demo.yaml`.

Browser tests (need a running server and Playwright's Chromium):

```bash
cd frontend && npx playwright install chromium
node e2e/smoke.mjs http://127.0.0.1:8000 /tmp/shots     # demo data; fails on console errors or missing content
                                                        # (start the server with --open-root demo to test "Add data")
node e2e/panes.mjs http://127.0.0.1:8000 /tmp/shots     # demo data: split panes
node e2e/errors.mjs http://127.0.0.1:8000 /tmp/shots    # demo data: error panes
node e2e/gallery.mjs http://127.0.0.1:8000 /tmp/gallery # `geoloupe gallery` (needs internet)
```

> **HPC / shared machines:** keep environments and caches out of the home directory. Point
> `UV_PROJECT_ENVIRONMENT` (or a `.venv` symlink), `UV_CACHE_DIR`, `npm_config_cache` and
> `PLAYWRIGHT_BROWSERS_PATH` to a project store, and link `frontend/node_modules` there too. The
> target folder must itself be called `node_modules` (Node finds packages by that name from the real
> path), e.g. `ln -s <store>/geoloupe-frontend/node_modules frontend/node_modules`. Never run
> `npm ci` in `frontend/` (even with `--dry-run`): it deletes the link and installs into the home
> directory. Install in the store folder instead:
> `cp frontend/package*.json <store>/geoloupe-frontend/ && (cd <store>/geoloupe-frontend && npm ci)`.

### Run the CI before you push

`scripts/ci_local.sh [WORKDIR]` runs the CI jobs of `.github/workflows/ci.yml` on a fresh clone of the
current commit: lint, mypy and tests on Python 3.12 and 3.13 (whose newer numpy and zarr have
stricter type stubs than 3.11), the web client with a clean `npm ci`, and the browser smoke test
with the demo data. `GALLERY=1` adds the gallery test on live public data. It creates one
environment per job in `WORKDIR` (default `$TMPDIR/geoloupe-ci`); delete it afterwards.

## Conventions

* **Python:** typed (mypy clean), formatted with `ruff format` (line length 100), linted with
  `ruff check`. Public functions have docstrings that say *what* and *why*. Errors that reach the user
  carry a message that says how to fix the problem (see `OpenError`, `ConfigError`).
* **TypeScript:** strict mode, ESLint (with the React hooks rules) and Prettier. Logic that can be tested
  without a browser lives in `src/lib/` and has Vitest tests.
* **No silent approximations.** If the engine aggregates, skips or approximates, it reports it (tile
  headers, layer metadata) and the UI shows it.
* **Bounded work per request.** New endpoints must have a size or cost limit with a clear error.
* **Tests next to the claim.** Resampling and compositing are tested against brute-force references, not
  against their own output. Add a test with every bug fix.
* **Docs in the same change.** Update README/ARCHITECTURE/docs when behaviour or formats change.
* Commit messages: imperative mood, a short subject line, a body that explains why.

## Making a change

1. Open an issue or describe the problem in the pull request.
2. Keep pull requests focused; one feature or fix each.
3. Make sure `pytest`, `ruff`, `mypy`, `npm test`, `npm run lint` and `npm run build` pass, and run the
   smoke test for UI changes.
4. Explain user-visible changes in the pull request description, with a screenshot for UI changes.

## Releasing

Bump `version` in `pyproject.toml` and `src/geoloupe/__init__.py`, build the client (`npm run build`),
then `uv build`. The wheel contains the client.
